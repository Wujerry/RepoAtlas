# Derive local project operations views from the shared core

RepoAtlas stores Project Collections, collection membership, environment observations, Task Run peaks and ports, AI evidence fingerprints, and attention acknowledgements in its local SQLite database. The shared Core owns these records and derives the structured Project Brief and Attention Items so desktop and MCP use the same semantics.

Task Run monitoring stays inside the structured Command Broker boundary. One application-level sampler refreshes the operating-system process and listening-port snapshots once for all active Task Runs every five seconds. System inspection runs outside the shared Core database lock, and peak values for the batch are persisted in one short transaction. It observes only launched process trees, uses fixed operating-system inspection commands for listening-port ownership, persists bounded peak values, and generates only `http` or `https` localhost endpoints. It does not add filesystem watching, shell evaluation, remote telemetry, or project-directory metadata.

Task Run history queries use project/time and status/time indexes. Repository Lineage uses a normalized indexed key maintained with Project detection rather than reparsing every Project's facts for each detail request. Attention acknowledgement and Collection membership are resolved in bounded batch queries; these derived views do not use per-item Project-detail lookups.

Project detail reads use stored facts exclusively, including when Repository Lineage is absent. They never fall back to a live Git process under the Core lock; explicit Project refresh updates the detected remote. The desktop dispatches detail reads to a blocking worker so waiting for the database does not block the UI thread.

Rapid project-list selection updates the selected row immediately and waits 120 milliseconds of stable selection before loading its workspace. A newer selection or return to Home cancels pending navigation; only the settled, successfully loaded Project records an open. Task-history, active-run and log reads also execute on blocking workers rather than the desktop thread. Project Continue Coding reads the existing session index and follows an already running refresh; only Home and explicit session actions initiate indexing.

The list-query effect depends on search/scope inputs, not the selected Project, and does not revalidate details after selection. The existing selection-validity effect handles Projects removed by filtering. Bootstrap, Project/search/Collection/Scan Root lists, attention and Dashboard snapshots, icons, and document preview reads use the shared blocking-worker boundary; waiting for Core never runs on the desktop thread for these reads.

The desktop also retains a bounded, memory-only overview cache: up to 20 entries each for Project details, Git and environment, eight each for README and AGENTS.md, and one installed-tool list. Revisited details appear immediately and are revalidated on every selection. Git freshness lasts 15 seconds, environment/tool discovery 60 seconds, and documents 30 seconds, checked on entry rather than by filesystem watching. Concurrent reads of the same key share a request. Expired data stays visible during refresh and on refresh failure, with pending/error feedback. Mutations, manual refresh, scans and external database changes invalidate Project overview resources through library reload; invalidation fences late results and refreshes active resources. Tool discovery has its own machine-wide TTL. No second persistence store or MCP cache/policy path is introduced.

Recent Project summaries start from at most six Project IDs and select each latest Task Run once, using an index that matches the timestamp expression and deterministic ID tie-breaker. The number of returned summaries must not hide repeated work over every historical run.

The desktop checks SQLite `data_version` on its existing Core connection every two seconds while visible and when returning to the window. Bootstrap captures the initial token before loading records. An external commit invalidates the current library cache and refreshes Projects, selected detail, Scan Roots, Collections, and the Dashboard without changing selection unnecessarily. Polls are single-flight and an unsuccessful refresh does not acknowledge the new token. This observes application records only; it does not watch or scan Project files.

Attention acknowledgement is versioned by the source condition. It is not deletion of the underlying Audit Event, Task Run, Project, or environment observation; when the source changes, the condition appears again.

The desktop Dashboard is another bounded derived view owned by the shared Core. Opening it performs read-only SQLite aggregation over non-archived Project state, Project Collections, current Task Runs, Attention Items, and terminal Task Run results from the previous seven days. Its recent Project and Task Run lists are capped, and collection activity is derived in batch. It does not refresh Git, read Project files, start a scan, record a Project open event, or create Audit Events. The Tauri adapter exposes the snapshot to the desktop, but MCP does not add a parallel Dashboard tool because Agents already have the narrower Project and Task Run contracts.
